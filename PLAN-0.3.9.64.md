## 3. Задача 1 — 0.3.9.64 → #299 «Активировать поле по умолчанию»

### Симптом
В окнах «Новое задание» (`ScheduledTaskEditWindow`) и «Новый сценарий» (`BackupScenarioEditWindow`)
поле ввода по умолчанию либо не активно, либо активно, но ввод не работает (глючит). Комментариев 0.

### Разведка (подтверждено кодом)
- **WPF `ScheduledTaskEditWindow`**: в конструкторе (строки 27–78) никакой установки фокуса на `NameBox` НЕТ.
- **WPF `BackupScenarioEditWindow`**: есть `Loaded += (_, _) => NameBox.Focus();` (строка 49) — без
  отложенного вызова и без `SelectAll`; при `ShowDialog()` WPF может передать фокус заголовку
  TabControl/первому контролу и «съесть» фокус из `Loaded` — отсюда «активно, но ввод не работает».
- **Avalonia оба окна**: `Opened`-обработчика нет вовсе (`ScheduledTaskEditWindow.Avalonia.cs:41-55`,
  `BackupScenarioEditWindow.Avalonia.cs:36-46`) — фокус остаётся на элементе, из которого вызвано окно.

### Гипотеза первопричины
Фокус на поле имени не устанавливается (WPF-задание, Avalonia-оба) либо устанавливается слишком
рано/без защиты (WPF-сценарий), из-за чего каретка не появляется или ввод не принимается.

### Файлы и правки
| Файл | Правка |
|------|--------|
| `Views/ScheduledTaskEditWindow.xaml.cs` | После инициализации полей добавить `Loaded` + `Dispatcher.BeginInvoke(...Idle)` → `NameBox.Focus()` (для нового задания — ещё и `SelectAll()`) |
| `Views/BackupScenarioEditWindow.xaml.cs` | Заменить строку 49 на отложенный вызов (`Loaded` → `Dispatcher.BeginInvoke` на `ApplicationIdle` → `Focus()` + `SelectAll()` для нового сценария) |
| `Views/ScheduledTaskEditWindow.Avalonia.cs` | Добавить `Opened += (_, _) => Dispatcher.UIThread.Post(_nameBox.Focus(), Background)` (+ `SelectAll()` для нового) |
| `Views/BackupScenarioEditWindow.Avalonia.cs` | То же самое |

### Критерий готовности (обе платформы)
1. Открыть «Утилиты» → «Задания по расписанию» → «Добавить»: курсор сразу в поле «Наименование», ввод печатается без щелчка.
2. «Сценарии резервирования» → «Добавить»: курсор в поле «Наименование», ввод работает.
3. Повторить с «Изменить» (редактирование) — имя выделено целиком, ввод затирает выделение.
4. `dotnet test` — набор проходит.

### Что НЕ менять
Логику сохранения/валидации, раскладку окон, темы.

## 4. Задача 2 — 0.3.9.65 → #297 «Добавление группы»

### Симптом
«Вкладка активная норм. А можно ещё и поле Наименование активировать сразу?» — фокус на поле имени
не всегда попадает (после фикса 0.3.9.57 активна вкладка «Основные»).

### Разведка (подтверждено кодом)
- **WPF** [`GroupEditWindow.xaml.cs:129-134`](Configuration%20Management/Views/GroupEditWindow.xaml.cs:129):
  `MainTabItem.IsSelected = true;` + `Loaded += (_, _) => { NameBox.Focus(); NameBox.SelectAll(); }`.
  Потенциальная проблема: `Loaded` срабатывает до реального показа/активации окна; TabControl при
  инициализации может перехватить фокус (классическое поведение WPF).
- **Avalonia** [`GroupEditWindow.Avalonia.cs:145-150`](Configuration%20Management/Views/GroupEditWindow.Avalonia.cs:145):
  `Opened += (_, _) => _nameBox.Focus();` — без SelectAll и без учёта результата `Focus()` (может вернуть
  false, если окно ещё не активировано).

### Гипотеза первопричины
Фокус ставится синхронно в момент, когда окно ещё не получило активацию/не завершило компоновку, —
поэтому срабатывает «не всегда» (платформенно-зависимо).

### Файлы и правки
| Файл | Правка |
|------|--------|
| `Views/GroupEditWindow.xaml.cs` | В `Loaded` заменить прямой `Focus()` на отложенный `Dispatcher.BeginInvoke(...ApplicationIdle)` → `Focus()` + `SelectAll()`; при необходимости `FocusManager.SetFocusedElement` |
| `Views/GroupEditWindow.Avalonia.cs` | В `Opened` заменить на `Dispatcher.UIThread.Post(_nameBox.Focus(), Background)` + `SelectAll()`; проверять результат и повторять при `false` (до N попыток) |

### Критерий готовности (обе платформы)
1. «Добавить группу» (контекстное меню/панель): окно на вкладке «Основные», курсор в «Наименование», ввод работает.
2. «Изменить» существующей группы: имя выделено целиком.
3. Повторное открытие 5+ раз подряд — фокус попадает стабильно каждый раз.
4. Служебные узлы «Без группы»/«Закреплённые» — поведение не меняется (вкладка «Цвет»).

### Что НЕ менять
Раскладку вкладок, выбор цвета/иконки, логику сохранения.

## 7. Задача 5 — 0.3.9.68 → #285 «Пожелание - переход к базе»

### Симптом (последний комментарий @7OH, 2026-09-25T21:30:35Z)

при длинном списке.

### Разведка (подтверждено кодом)
- Вьюмодель корректна: [`MainViewModel.Commands.cs:1284-1319`](Configuration%20Management/ViewModels/MainViewModel.Commands.cs:1284)
  (и Avalonia-аналог) — переключение на «Все базы», сброс фильтров, `ExpandPathTo` (дважды),
  `RebuildGroupTree`, `SelectedInfobase = ib`, `RevealFindInListRequested`.
- **WPF** [`MainWindow.Tree.cs:252-384`](Configuration%20Management/Views/MainWindow.Tree.cs:252):
  `RevealAndSelectAfterRebuild` раскрывает предков (`FindTreeViewItemForData` → `BringIntoView`),
  `MainTree.UpdateLayout()`, затем `FindTargetContainer(target, leaf)`. Если контейнер не найден —
  до `MaxRevealAttempts = 3` повторных проходов (строки 332-337) **без сдвига прокрутки к цели**.
  При `VirtualizingStackPanel` (`MainWindow.xaml:1170-1183`, Recycling, ScrollUnit=Pixel) контейнер
  строки далеко за вьюпортом внутри длинной раскрытой группы не создаётся никогда — поиск всегда
  возвращает null, «перехода не происходит».
- **Avalonia** [`MainWindow.Avalonia.Scroll.cs:167-254`](Configuration%20Management/Views/MainWindow.Avalonia.Scroll.cs:167):
  та же схема: `FindFindInListRow` → `ContainerForItemWithin`; при null — до `MaxRevealAttempts = 3`
  повторных попыток без прокрутки.

### Гипотеза первопричины
При цели ниже реализованного диапазона виртуализации контейнер не материализуется, а «добирающие»
проходы не прокручивают список к месту цели (нет шага «прокрутить к домашней группе/цели перед поиском»).
Первый переход «внутри группы с базами» иногда срабатывает, потому что цель попадает в диапазон
материализации после `BringIntoView` предков; цель «ниже этой группы» — за пределами диапазона.

### Правки
**WPF [`MainWindow.Tree.cs`](Configuration%20Management/Views/MainWindow.Tree.cs:252):**
1. В ветке `_revealFindInListPending` при `item == null` — принудительно материализовать дерево:
   - временно `VirtualizingPanel.SetIsVirtualizing(MainTree, false);`
   - `MainTree.UpdateLayout();`
   - повторить `FindTargetContainer(target, leaf)`;
   - при успехе — `ApplySelection`/`ScrollSelectedIntoView`, затем вернуть
     `VirtualizingPanel.SetIsVirtualizing(MainTree, true)` + `UpdateLayout()` (восстановить прокрутку к цели).
2. Увеличить `MaxRevealAttempts` (например, до 6) и в повторных проходах первым делом вызывать
   `BringIntoView` контейнера домашней группы (`FindTreeViewItemForData(leaf)`) + `UpdateLayout`.

**Avalonia [`MainWindow.Avalonia.Scroll.cs`](Configuration%20Management/Views/MainWindow.Avalonia.Scroll.cs:167):**
1. В `RevealFindInListAttempt`: если контейнер цели не найден, но найден контейнер домашнего узла —
   `homeItem.BringIntoView()` (при необходимости — с повторами), затем снова поиск цели.
2. Увеличить `MaxRevealAttempts` до 6–8.
3. Проверить `AutoScrollToSelectedItem` у `LeveledTreeView`; при необходимости добавить в
   [`LeveledTreeView.Avalonia.cs`](Configuration%20Management/Controls/LeveledTreeView.Avalonia.cs)
   метод принудительной прокрутки по данным (например, `EnsureDataVisible(data)` через
   внутренний `ScrollViewer` с итеративной прокруткой).

### Критерий готовности (обе платформы, из всех разделов: Все базы / Избранное / Недавние / Закреплённые)
1. База в короткой группе — переход работает (регрессии нет).
2. База в длинной раскрытой группе (50+ баз перед ней) — переход выделяет и показывает строку.
3. База в свёрнутой вложенной группе в конце длинного списка — цепочка раскрывается, строка показывается.
4. Повторные вызовы подряд к разным целям (выше и ниже предыдущей) — каждый раз корректный переход.
5. Ctrl+T и пункт контекстного меню «Найти в списке» — одинаково.
6. Обычные пересборки дерева (редактирование, таймер синхронизации) не меняют поведение

### Что НЕ менять
