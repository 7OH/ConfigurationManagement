Исправлено в версии **0.3.9.304**.

**Причина.** После закрытия контекстного меню кликом по другой строке строка становилась
активной, но «через мгновение» выделение пропадало (воспроизводилось и без мультивыделения).
Пять прежних попыток (0.3.9.277/291/299/300/302) не помогли, потому что строились на двух
слабостях одновременно:

1. **Применение выбора в момент `ContextMenu.Closed` нестабильно.** Попап только что закрылся,
   и контейнеры под курсором ещё перерабатываются виртуализацией (`VirtualizingStackPanel`,
   `VirtualizationMode="Recycling"`): выбор ставится на контейнер, который дальше
   переиспользуется, и `IsSelected` «уезжает».
2. **Гашение повторной доставки клика лишало систему единственного устойчивого пути выбора.**
   После освобождения захвата попапа WPF повторно доставляет «хвост» MouseDown в дерево — это
   штатный путь `OnInfobaseTree_PreviewMouseLeftButtonDown`, применяющий выбор к ЖИВОМУ
   контейнеру (надёжен под Recycling). Гася его снимком, мы оставались только с нестабильным
   «применением в Closed» — отсюда «сначала видно, потом пропадает».
3. Дополнительно: `IsSelected` не связан с моделью (двустороннюю привязку убрали ранее из-за
   рекурсии/StackOverflow), поэтому после переработки контейнеров выделение не восстанавливается
   само — только явным применением.

**Новая стратегия — «штатный выбор + однократный fallback + стабилизация IsSelected».**

1. **Штатный путь выбора восстановлен.** В `TryApplyTreeClickAfterMenuClosed`
   ([`MainWindow.Hotkeys.cs`](Configuration%20Management/Views/MainWindow.Hotkeys.cs)) выбор
   больше НЕ применяется синхронно: фиксируется только клик (снимок + флаг
   `_menuClosePendingApply` + целевая база/секция). Повторная доставка MouseDown в дерево
   обрабатывается ШТАТНО (`ClearBatchSelection` + `ApplySelection` по живому контейнеру) и
   снимает флаг.
2. **Fallback** через `Dispatcher.BeginInvoke(DispatcherPriority.Input)`: если к моменту
   исполнения флаг ещё взведён (повторной доставки не было) — выбор применяется по данным
   (`SelectTreeRowByData`) и снимается флаг. Fallback идемпотентен и не вмешивается, если
   пользователь успел перевыбрать другую строку.
3. **Стабилизация `EnsureSelectionStable`** ([`MainWindow.Tree.cs`](Configuration%20Management/Views/MainWindow.Tree.cs)):
   после применения выбора — одноразовая подписка на `LayoutUpdated` (до 3 срабатываний или
   ~200 мс); при расхождении `SelectedInfobase` и `IsSelected` контейнера выбор восстанавливается
   по данным. Метод НИКОГДА не вызывает `ClearBatchSelection`/`ToggleBatchSelection` —
   мультивыделение не затрагивается.
4. **Снимок записывается только для простого левого клика БЕЗ модификаторов**
   (`ShouldRecordMenuCloseSnapshot`, [`BatchSelectionHelper.cs`](Configuration%20Management/Services/BatchSelectionHelper.cs)):
   Ctrl/Shift-клики уходят штатной логике мультивыделения и не подавляются.
5. **Avalonia/Linux** — зеркально: убрано подавление повторной доставки
   (`OnTreeMenuCloseClickDedup_PointerPressed` больше не гасит событие), выбор применяет штатный
   `OnRowPointerPressed` контрола; fallback по данным + стабилизация через
   `Dispatcher.UIThread.Post`/`LayoutUpdated`; новый `LeveledTreeView.FindRowForData` ищет
   контейнер с учётом секции («Закреплённые» vs обычный список).

Тесты: 4 новых сценария в
[`BatchSelectionHelperTests.cs`](ConfigurationManagement.Tests/BatchSelectionHelperTests.cs)
(снимок только без модификаторов; идемпотентность fallback; стабилизация не трогает
мультивыделение; регресс `IsSameClick` для повторной доставки); полный набор **1721** тест
зелёный, кросс-сборка Linux без ошибок.

**Как проверить:**

1. Мультивыделение (Ctrl/Shift) → правый клик → левый клик по другой строке: строка становится
   активной и **остаётся** активной (не пропадает через мгновение).
2. Без мультивыделения: правый клик по строке → меню → левый клик по другой строке — то же.
3. Ctrl/Shift-клики при открытом меню не ломаются (мультивыделение меняется штатно).
4. Двойной клик по строке (запуск базы) после закрытия меню работает.
5. Повторить на Linux (Avalonia).

Нужна ручная проверка на Windows — оконный стек юнит-тестами не покрывается.
