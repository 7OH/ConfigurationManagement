Исправлено в версии **0.3.9.305** (Windows/WPF и Linux/Avalonia; седьмая итерация).

**Что было.**

Проблема сохранялась после шести попыток (0.3.9.277, 0.3.9.291, 0.3.9.299, 0.3.9.300, 0.3.9.302, 0.3.9.304): «Выделение всё ещё пропадает после закрытия контекстного меню при клике мышью на другой строке». Разбор текущей логики выявил три слабых места:

1. **Стабилизация `IsSelected` вызывалась только в одном из трёх путей** применения клика (путь A — совпавшая повторная доставка `MouseDown`). Если снимок клика был сброшен событием `MouseUp` раньше (путь C), клик обрабатывался как обычный — **без** стабилизации, и переработка контейнеров (`VirtualizingStackPanel`, `Recycling`) «увозила» выделение.
2. **Окно стабилизации было коротким** (3 срабатывания `LayoutUpdated` / ~200 мс), а отложенная переработка контейнеров после закрытия попапа может происходить позже. Дополнительно видимая-но-нереализованная виртуализацией строка считалась «согласованной» — восстановление не выполнялось.
3. **Сброс pending-состояния при деактивации окна** мог отменять применение клика, когда контекстное меню ещё только закрывалось (кратковременная деактивация главного окна).

**Что сделано.**

1. **Диагностика `CM_MENUCLOSE_TRACE=1`** (по образцу `CM_COLUMNS_TRACE`): при установке переменной окружения в `%TEMP%\cm_menuclose_trace.log` пишется полная последовательность событий клика, закрывшего контекстное меню: запись снимка (`OnContextMenuClosed`), `MouseUp`, `MouseDown` (путь A/C, совпадение снимка), срабатывание fallback, каждый проход стабилизации и контрольный дамп через 500 мс (`SelectedItem`, `SelectedInfobase.Id`, `container.IsSelected`, размер пакетного набора).
2. **Стабилизация во всех путях** ([`Views/MainWindow.Events.cs`](Configuration%20Management/Views/MainWindow.Events.cs), [`Views/MainWindow.Avalonia.Events.cs`](Configuration%20Management/Views/MainWindow.Avalonia.Events.cs)): `EnsureSelectionStable` запускается при любом обычном левом клике, которым закрыли контекстное меню, — и при совпавшей повторной доставке (путь A), и когда снимок уже сброшен до доставки (путь C); признак один — снимок присутствовал в момент начала клика. Fallback (путь B) стабилизирует, как и раньше.
3. **Стабилизация доводится до сходимости** ([`Views/MainWindow.Tree.cs`](Configuration%20Management/Views/MainWindow.Tree.cs)): подписка на `LayoutUpdated` работает до 10 проходов / 1000 мс (раньше 3 прохода / ~200 мс); видимая-но-нереализованная виртуализацией строка больше НЕ считается согласованной — выбор восстанавливается по данным (`SelectTreeRowByData`, идемпотентен); с новым кликом пользователя стабилизация немедленно прекращается (`ReferenceEquals(SelectedInfobase, target)`).
4. **Сброс при деактивации — только после фактического закрытия меню** ([`Views/MainWindow.xaml.cs`](Configuration%20Management/Views/MainWindow.xaml.cs)): pending-состояние сбрасывается, только когда открытых контекстных меню нет (`_openContextMenus.Count == 0`); ложная деактивация в момент закрытия попапа не отменяет применение клика.
5. Логика мультивыделения (Ctrl/Shift, правило секций #326), двойной клик (запуск базы) и DnD **не менялись**.

**Как проверить:** обновитесь до **0.3.9.305**; выделите несколько строк (Ctrl или Shift, в любой секции) → правый клик (контекстное меню) → левый клик по другой строке: строка остаётся активной, выделение не пропадает «через мгновение». Повторите без мультивыделения (правый клик → клик по другой строке) и в «Закреплённых». Если баг сохранится — установите переменную окружения `CM_MENUCLOSE_TRACE=1`, воспроизведите сценарий один раз и пришлите файл `%TEMP%\cm_menuclose_trace.log` (или его фрагмент): по логу будет точно видно, какой путь (A/B/C) и какое звено рвётся.
