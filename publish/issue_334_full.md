## Комментарий 1 от sivatorov (2026-10-01T16:46:09Z)

Исправлено в версии **0.3.9.248** (Windows/WPF и Linux/Avalonia).

**Что было сломано.** В релизах 0.3.9.233+ попытка проверить обновления платформы
(F9 / окно «Обновление платформы 1С», Ctrl+F9) заканчивалась неприятным сценарием:

1. **«Мелькание» панели статуса** — внизу окна на долю секунды появлялась и тут же
   исчезала панель прогресса/журнала, даже если проверка мгновенно завершалась сбоем.
2. **Ошибка без понятного объяснения** — сообщение об ошибке либо не показывалось вовсе,
   либо появлялась пустая строка, когда провайдер возвращал статус ошибки без ключа
   локализации.
3. **Прогресс «прыгал» в 1** — при любом исходе операции (в том числе при сбое) прогресс
   принудительно выставлялся в 1, создавая ложное впечатление «всё скачалось», хотя
   ничего не скачалось.
4. **Неперехваченные исключения провайдера** — исключения из цепочки `OneCUpdatesService`
   (сетевые сбои, редиректы, изменившаяся структура страницы каталога) могли всплывать
   до уровня ViewModel и ронять операцию без диагностики.

**Причины.**

- Панель статуса показывалась WPF-стилем через `DataTrigger` на `IsBusy`; при быстром
  сбое `IsBusy` успевал пройти `false → true → false` в пределах одного отрисовываемого
  кадра — панель «мигала». На Avalonia видимость панели переключалась напрямую из
  обработчика `PropertyChanged` — то же мгновенное появление/скрытие.
- В `finally` метода проверки безусловно выполнялось `Progress = 1` — значение прогресса
  не различало «успех» и «ошибку».
- В ветке ошибки использовался ключ локализации из результата провайдера без проверки на
  пустоту; при `ErrorKey = ""` пользователю показывалась пустая строка. Сама операция
  бросала исключение наружу (перехват в ViewModel отсутствовал).

**Как исправлено.**

- **Перехват ошибок провайдера.** `CheckUpdatesAsync` теперь оборачивает обращение к
  сервису в `try/catch`: любое исключение (сеть, вход на `login.1c.ru`, изменившаяся
  структура страницы каталога) превращается в понятное сообщение — в журнал окна,
  системное уведомление об ошибке и запись `IAppLogger.Error` с типом исключения (без
  паролей/токенов). Операция завершается штатно, приложение не падает
  ([`PlatformUpdateViewModel.cs`](Configuration%20Management/ViewModels/PlatformUpdateViewModel.cs)).
- **Fallback пустого ключа ошибки.** Если провайдер вернул статус ошибки без ключа
  локализации — подставляется общий ключ сетевой ошибки
  `PlatformUpdate.Error.NetworkError`, пустая строка пользователю не показывается.
- **Анти-мигание.** Панель статуса показывается только при старте операции и скрывается
  с задержкой **500 мс** после завершения (DispatcherTimer, обе платформы): при
  мгновенном сбое панель успевает показать текст ошибки и не «мигает»
  ([`PlatformUpdateWindow.xaml`](Configuration%20Management/Views/PlatformUpdateWindow.xaml),
  [`PlatformUpdateWindow.xaml.cs`](Configuration%20Management/Views/PlatformUpdateWindow.xaml.cs),
  [`PlatformUpdateWindow.Avalonia.cs`](Configuration%20Management/Views/PlatformUpdateWindow.Avalonia.cs)).
- **Прогресс при ошибке.** `Progress` больше не «прыгает» в 1 в `finally`: при ошибке он
  остаётся 0, видимой «загрузки» нет.

**Как проверить.**

1. Установите версию **0.3.9.248** (Windows или Linux).
2. Откройте «Обновление платформы 1С» и нажмите «Проверить обновления» (F9 / Ctrl+F9)
   при недоступном портале или без входа на сайт 1С — вместо мелькания и пустой ошибки
   внизу окна появится понятное сообщение об ошибке (сетевая ошибка / требуется вход /
   каталог не найден), а также системное уведомление об ошибке; приложение продолжает
   работать.
3. Повторите проверку при рабочем подключении — каталог версий загружается как раньше.
4. Windows и Linux ведут себя одинаково (панель статуса не «мигает» в обоих случаях).

Тесты: `PlatformUpdateViewModelTests` (fake-делегат бросает исключение → статус
«ошибка», журнал + уведомление, прогресс остаётся 0; пустой ключ ошибки → общий ключ
сетевой ошибки), регрессия `PlatformUpdateServiceTests`, `PlatformUpdateMatcherTests`,
`PlatformUpdateViewModelTests` — зелёные; `dotnet build -p:BuildLinux=true` — без ошибок.

## Комментарий 3 от sivatorov (2026-10-02T05:56:14Z)

Исправлено в версии **0.3.9.260** (Windows/WPF; Linux/Avalonia не затронута — там автопрокрутка уже
шла через `Dispatcher.UIThread.Post`).

Окно «Обновление платформы 1С» больше не падает при проверке обновлений с ошибкой
`InvalidOperationException` «Вызывающий поток не может получить доступ к данному объекту».

**Причина.** `PlatformUpdateViewModel.AppendLog` уведомляет UI (`OnPropertyChanged(LogText)`)
из фоновых задач — `CheckUpdatesAsync` использует `ConfigureAwait(false)`, поэтому
обработчик `PropertyChanged` окна выполнялся на фоновом потоке. Окно
([`Views/PlatformUpdateWindow.xaml.cs`](Configuration%20Management/Views/PlatformUpdateWindow.xaml.cs))
вызывало `LogBox.ScrollToEnd()` прямо в этом обработчике — WPF бросал `Dispatcher.VerifyAccess`
при каждом обновлении журнала, и окно падало во время проверки каталога версий.

**Как исправлено.** Автопрокрутка журнала перенесена в UI-поток:
`Dispatcher.BeginInvoke(new Action(() => LogBox?.ScrollToEnd()))` + защита `?.` на случай закрытия
окна до исполнения отложенного вызова. Контракт ViewModel не менялся.

**Про пустой ответ портала.** В момент падения `releases.1c.ru/project/Platform83` возвращал
пустую страницу — это отдельный внешний фактор, который падение НЕ вызывает: провайдер
([`PlatformUpdateService`](Configuration%20Management/Services/PlatformUpdateService.cs)) маппит
пустое тело/HTTP-ошибку в статус `NetworkError` без исключений, а окно показывает пользователю
понятное сообщение «Ошибка сети при обращении к сайту 1С» (журнал + уведомление, ключ
`PlatformUpdate.Error.NetworkError`). WARN-строки в журнале приложения — штатное поведение.

**Тесты.** Добавлены регрессионные тесты: `AppendLog` и запуск `CheckUpdatesAsync` из `Task.Run`
поднимают уведомления `PropertyChanged` без исключений; сценарий «пустой ответ провайдера» —
статус ошибки без проброса исключения
([`PlatformUpdateViewModelTests`](ConfigurationManagement.Tests/PlatformUpdateViewModelTests.cs)).
Полный набор `dotnet test` зелёный (1477), кросс-сборка Linux без ошибок.

**Как проверить в 0.3.9.260.**

1. Установите 0.3.9.260 на Windows.
2. Откройте «Обновление платформы 1С» (Ctrl+F9): при доступном портале каталог загрузится,
   при пустом ответе/ошибке сети в журнал и уведомление выведется «Ошибка сети при обращении
   к сайту 1С».
3. Окно не падает, журнал прокручивается к последней строке; «Проверить обновления»,
   «Скачать и установить» и «Только скачать» работают как раньше.

Исправлено в версии **0.3.9.287** (Windows/WPF и Linux/Avalonia).

**Что было:** «Для входа на portal.1c.ru не задан логин» + пустой ответ каталога платформы в окне «Обновление платформы 1С» — выбранная учётная запись ИТС не доходила до [`GetCredentials()`](Configuration%20Management/Services/OneCUpdatesService.cs), а при отсутствии настроенных учётных данных служба возвращала голый NetworkError вместо понятного сообщения.

**Как исправлено** ([`OneCUpdatesService.cs`](Configuration%20Management/Services/OneCUpdatesService.cs)):

1. **Учётная запись ИТС доходит до `GetCredentials()`.** Выбор учётной записи из настроек/справочника проверен по всей цепочке; после фикса #333 пункт в списках выбора отображается именем, а не ключом, поэтому выбирается именно та запись, которую видит пользователь.
2. **Понятное сообщение вместо голой ошибки.** При отсутствии настроенных учётных данных службы показывают явное сообщение «Требуется вход на сайт 1С» вместо технического NetworkError.

**Тесты.** [`UpdateCheckCatalogTests`](ConfigurationManagement.Tests/UpdateCheckCatalogTests.cs) дополнены: 302 без Location → `AuthRequired`; 302 без Location → вход на portal.1c.ru → повторный запрос каталога → найдена новая версия; зелёный путь 200 с HTML. 2. В окне «Обновление платформы 1С» при отсутствии настроенных учётных данных ИТС должно появиться понятное сообщение «Требуется вход на сайт 1С», а не голый NetworkError.

## Комментарий 7 от sivatorov (2026-10-03T06:21:35Z)

Исправлено в версии **0.3.9.297** (Windows/WPF и Linux/Avalonia).

**Что было сделано.**

Причина была в двух местах, и оба устранены.

1. **Учётные данные ИТС не доходили до входа на portal.1c.ru.** Сервис
   `OneCUpdatesService` создавался без справочника учётных записей — поле
   `IItsAccountsStore` было `null`, и `GetCredentials()` читал только устаревшие
   поля настроек `UpdatesLogin/UpdatesPassword`. Если они были пусты, вход даже не
   начинался: «Для входа на portal.1c.ru не задан логин» (ваша строка из лога).
   Теперь в сервис внедряется `IItsAccountsStore`, и при входе используется
   учётная запись из справочника (`its_accounts.json`, включая выбранную или
   «Основную»); старые поля настроек остались только как запасной вариант.

2. **Цепочка CAS-входа доведена до конца.** Раньше после POST формы входа при
   ответе 302 проверялось только, что Location не содержит «login», — и вход
   считался успешным, хотя GET по `security_check?ticket=…` (где выпускается
   сессионная cookie) не выполнялся. Теперь:
   - GET формы входа выполняется по полному URL редиректа (с параметром
     `service=https://releases.1c.ru/public/security_check`);
   - из формы извлекается скрытый токен `execution` (разбор расширен — в том числе
     для одинарных кавычек и другого порядка атрибутов);
   - POST логина;
   - если POST вернул 3xx, редиректы проходятся вручную до лимита шагов: GET по
     каждому Location через общий HTTP-клиент, сессионные cookie накапливаются в
     общем `CookieContainer`; цепочка считается успешной, когда получена
     200-страница вне страницы входа либо выполнен редирект на хост, отличный от
     login.1c.ru (после обязательного GET этого Location);
   - затем исходный запрос каталога повторяется.
   Вход выполняется один раз за сессию службы; защита от зацикливания — общий
   лимит шагов.

3. **Пошаговая диагностика в журнале.** Перед входом пишется имя учётной записи
   без пароля (`ResolveAccountName`: имя записи из справочника, иначе «Основная»,
   иначе «не задана»); каждый шаг цепочки — `[Updates] Редирект входа {status}
   (шаг N): '<Location>'`; результат — `[Updates] Вход на portal.1c.ru выполнен
   (шагов: N)` или понятное сообщение о неудаче (статус и Location).

**Тесты.** Добавлены тесты `UpdateCheckCatalogTests` и `PlatformDownloadViewModelTests`:
учётка из store используется при запросе кредов даже при пустых старых настройках;
фолбэк на старые настройки при пустом справочнике; полный сценарий «302 на
login.1c.ru → форма → POST → 302 на security_check?ticket=… → GET → 200 → каталог
получен» (с проверкой, что POST ушёл с логином из store); явная проверка следования
за редиректом после POST; при отсутствии кредов — понятная ошибка AuthRequired.
Существующие тесты сценариев 302 продолжают проходить.

**Как проверить:**

1. Установите версию **0.3.9.297**.
2. В «Общих настройках» добавьте учётную запись ИТС (или задайте её «Основной»);
   старые поля логина/пароля в настройках можно оставить пустыми.
3. Откройте «Обновление платформы 1С»: каталог версий должен загрузиться.
4. В журнале приложения должны быть видны имя учётной записи и шаги входа
   (`Вход на portal.1c.ru выполнен`).

```
[WARN] retryAfterLoginStill302=true: после «успешного» входа повтор исходного запроса снова дал
       302 на login.1c.ru (фантомный успех); второй вход в рамках операции не выполняется.
→ PlatformUpdate.Error.AuthRequired
```

Найдена причина: вход возвращал **мгновенный Success по имени cookie**. `HasPortalSessionCookie()`
проверяла только имена (`TGC` / `JSESSIONID*` / `*session_id*` / `SESSION`) без атрибутов
(`Domain`, `Path`) и без проверки «живости» сессии на сервере. Любая cookie-заглушка WAF/CDN
с «подходящим» именем попадала в контейнер через `ApplySetCookieToContainer` и считалась валидной
сессией — повтор исходного запроса снова уходил в 302 на login.1c.ru. Вдобавок локальный флаг
`loginTried` разрешал не более одной попытки входа за вызов: при 302 после «успешного» входа
повторный вход со свежей формой не выполнялся — автообновление платформы не получало каталог версий.

**Как исправлено** (общий корень для #323/#330/#334 — в [`Services/OneCUpdatesService.cs`](Configuration%20Management/Services/OneCUpdatesService.cs)):

1. **Устранён ложный Success по cookie-заглушке**: ранний выход по имени cookie заменён честной
   проверкой «живой» сессии — пробный GET по исходному URL операции (каталогу): если ответ 2xx
   и не страница входа — сессия жива, вход не выполняется и лимит попыток не тратится; если
   сессия мертва — cookie портала снимаются и выполняется полный вход (GET формы → POST →
   цепочка редиректов).
2. **Повторный вход при `retryAfterLoginStill302=true`**: вместо одноразового флага `loginTried` —
   счётчик попыток в рамках одного вызова (`MaxLoginAttemptsPerOperation = 2`). При повторном
   302→login после «успешного» входа теперь выполняется **повторный вход со свежей формой**
   (новый `execution`/`lt`), перед которым снимаются мусорные cookie хостов
   `login.1c.ru`/`releases.1c.ru` (`ClearPortalCookies()`). Маркер `retryAfterLoginStill302`
   остаётся диагностическим и появляется только после исчерпания повторов либо при
   заблокированном лимите сессии — тогда возвращается честный
   `AuthRequired`/`AuthFailed`/`LoginLimitReached`.
3. **Ужесточён `HasPortalSessionCookie()`**: cookie учитывается только с доменом `.1c.ru` и
   `Path=/` (или покрывающим корень) — cookie-заглушки с чужим доменом/путём сессией портала
   больше не считаются.
4. **Диагностика**: инвентаризация cookie контейнера в начале каждого входа
   (`Вход: cookie контейнера: …`) и результат пробной проверки живой сессии (`alive=True/False`)
   — по журналу видно, какая cookie присутствовала и почему принято решение.

**Как проверить.**

1. Обновитесь до **0.3.9.307** (Windows или Linux).
2. Откройте «Утилиты → Автообновление платформы 1С» (Ctrl+F9) при настроенной записи ИТС
   («Основная»).
3. Ожидание: **список версий платформы загружается**, доступна актуальная версия для
   сравнения/скачивания; в журнале окна нет `PlatformUpdate.Error.AuthRequired` и
   `retryAfterLoginStill302=true`.
4. По вашему замечанию проверьте и каталог `Platform85` — ник параметризован с 0.3.9.301,
   выбор должен быть доступен в интерфейсе.
5. При неудаче входа (например, временная блокировка портала) — понятное раздельное сообщение
   и совет: запись ИТС «Основная», при лимите — подождать ~10 минут.
6. Повторите шаги на Windows и Linux — вход реализован в общем сервисе, обе платформы используют
   его напрямую.
